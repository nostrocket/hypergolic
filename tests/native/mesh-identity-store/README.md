# Native Mesh credential and membership store

This unexposed component adds no Expo API, autolink, socket, signing, grant or supported Mesh capability. The native coordinator remains responsible for actual account/source authority, invitation bootstrap, pairing consent, both BIP340 verifications and fresh mTLS possession before minting a membership token. Host's event/forward/blob store is separate.

## Native composition API

Both platforms implement NativeMeshIdentityStore with matching bounded binary snapshots. Java types/constructors are package-internal in `org.nostrocket.hypergolic.mesh`; Swift types are module-internal. No public approved-boolean or arbitrary record factory exists.

- AccountLease(account,epoch,vaultRevision,current): only the actual selected local-account coordinator constructs it. Its bounded, synchronous current predicate must cover account/epoch/vault/selected signing method/unlocked/foreground lifetime. It is not a source/publication or15s job permit. Closing the store permanently revokes that lease before destroying its master; coordinator also calls lease.revoke on lifecycle changes. The C owner current callback uses this native lease.isCurrent, so logical revocation does not wait for eventual key destruction.
- Backend: native authenticated storage adapter. Android NativeMeshIdentityFile.open uses a dedicated account-specific AES256-GCM Keystore alias and noBackup encrypted file. iOS NativeMeshIdentityKeychain uses a dedicated generic-password service, nonsynchronizable WhenUnlockedThisDeviceOnly, default app group and data-protection Keychain.
- CredentialPort.importDER: actual native TLS import only. initialize(producer) receives a single synchronous C credential-store sink, validates exact DER/pin through that port, persists and wipes owned temporary buffers. No secret byte/string getter exists. Snapshot holds owned DER only while this account store is open.
- withCredential returns a bounded native borrow. At most four simultaneous borrows share ONE imported opaque credential per account store. Its withNative callback receives the actual native credential only synchronously under the store lock, for the coordinator's TLS creator; no Expo access exists. Borrow.close releases a borrow, not the master credential. Store.close revokes its lease before waiting for the store lock and destroys the master exactly once after synchronous native callbacks drain; existing C TLS sessions retain its key until their actual drain/destroy. Native port must serialize actual C close with TLS operations, or logically revoke immediately and schedule destruction on its owning actor. Never free a C key concurrently with an active C call.
- VerifiedMembershipCommit(lease,circleRevision,local340B,remote340B,currentProof): coordinator-only one-use token. It is created AFTER actual mutual role signatures/confirmations and fresh mTLS proof. The proof predicate must cover the original pairing deadline, exact invitation, confirmations, transport proof and cancellation. Store independently checks the two role-specific transcripts agree, own account/local pin, peer pin, different nonces, valid expiry field and exact pairing ID; circle revision and exact lease must match. This component has no real signature verifier or proof-token factory.
- stage(expectedGeneration,commit) persists PENDING. Exact same pairing ID plus both exact role bindings reconciles without another write/signature; conflicting same ID or already-bound remote pin is denied. Pending records never contribute active peer counts, including after process/store reopen.
- MembershipPromotion(lease,circleRevision,pairingId,bindingsDigest,currentProof) is a separate one-use native bilateral-completion proof. promote makes only that exact pending record ACTIVE; an already-active exact record is idempotent. No automatic active transition follows a remote signature, transport reachability, stage success or uncertain result. Reconciliation reads the stored ID/digest/state and never re-signs automatically.
- promote/remove synchronously invoke the native revoker before persistence and advance circle revision. Successful return supplies the new durable revision for coordinator/authority/store synchronization. Any uncertain storage operation closes the account store and revokes. Removal is acknowledged only after durable success. Background/close does not erase persistent membership; every later connection still needs current paired mTLS/source authority.

One store handle per account and at most16 open account handles are permitted per process. Mutations are serialized; expected generation and token circle revision are checked before/after native proof predicates. The last stored snapshot must byte-match before a replacement. This is not a multi-process transaction or OS anti-rollback mechanism. The app must keep one coordinator/owner. Store/native callbacks are synchronous, bounded and run under recursive store locks. Current/RNG predicates must not acquire coordinator locks in the opposite order; never call store while holding a lock that its native C current/entropy/IO callback may acquire. No UI, blocking handshake or worker wait belongs inside a borrow callback. The C caller must serialize credential/session access, and every BIO enqueue still needs its own current source/connection permit and original frame deadline.

## Storage and format

Limits are BOTH32 remote device records AND16 distinct account identities across them, including the selected account if another same-account device is paired. Multiple devices per account are allowed; public native view returns pins/account/ID/digest/state, not secrets. Active account count deduplicates active records only. DER key and certificate each1..2048B; total snapshot max128KiB. Format is fixed binary, not general JSON: magic HGMI/version1, account32B, generation and circle revision uint64BE within JS-safe nonnegative range (generation>0), two DER uint16 lengths, local SPKI SHA25632B, record count u8, DER payloads, then681B per record (state0/1 plus both340B signed role bindings). Trailing/truncated/unknown bytes, wrong account/pins/roles/nonces and duplicate ID/pin are denied. Persisted completed pairing is allowed past original invitation expiry; current promotion authority must still be valid. Actual BIP340 validation is coordinator-owned, not inferred from these structural checks.

Android authenticates fixed header+account as AES-GCM AAD with OS-generated12B IV and128-bit tag. Missing key with existing file, missing file with existing alias, residual write file, corruption and uncertain durability never reset/create new identity. Production checks file fsync, POSIX rename and directory/parent fsync, then exact readback. Tests use this same FileStore with real files, software test keys and injected OS barriers. API28+ sets unlockedDeviceRequired; API24–27 relies on native foreground/current plus Keyguard locked checks and close/wipe. Do not claim equivalent hardware or OS unlocked-only enforcement there.

iOS uses SecItemAdd/Update with exact absence/conflict checks and readback, no fallback namespace, shared group or synchronization. A native Security Port seam tests exact queries/statuses without writing the host's real Keychain. Swift/Foundation, JVM/crypto and OS APIs may copy bytes internally; owned mutable buffers are wiped but this is not proof that every managed/OS copy was erased. Transport credential rotation/deletion and account recovery require a separate explicit native coordinator action; there is no silent key rotation or destructive recovery API here.

## Reproduction and evidence limits

From the repository root, with existing tools and the passing TLS proof archives:

```sh
python3 -B tests/native/mesh-identity-store/run.py \
  --tls-build /tmp/mesh-tls-proof \
  --output /tmp/mesh-identity-proof-fresh
```

Output must be new. The runner hash-checks final TLS source/header and exact linked archive bytes, compiles actual Java production against Android SDK with Java8 API targeting, executes Java17 host tests, executes Swift6/CryptoKit/Security-port tests, and compiles actual production Swift for iPhoneOS ARM64. No packages, OS-keystore writes, real Keychain writes, app builds, device calls or network occur. C test adapter uses actual current TLS generation/store/import/pin/destruction with a fresh disposable non-account key; its JNI byte getters exist ONLY in test sources. Temporary plaintext fixture files are deleted after recording hashes. Other retained file evidence is ciphertext under a software test key that is never persisted.

Controls cover exact Java/Swift snapshot parity, staged-pending/reopen/explicit promotion, duplicate/conflict reconciliation, stale lease/circle/token, reentrant current loss/closure and nested native-call drain (including exceptions), concurrent close invalidation before drain, one master/four borrows, source close,32/16 caps, same-account/multiple-device and joiner-role records, malformed snapshots/DER, account/AAD tamper isolation, absent key/file/residue, checked real-file pre/post-rename faults, unknown durability and Keychain locked/error/status behavior. These are native host/component and compilation results. Actual AndroidKeyStore/phone Keychain, real mutual pairing, LAN permissions/discovery, coordinator/bootstrap/registry/signing and full Mesh acceptance remain open. Original failed/interim runs are preserved outside source and are not relabeled final passes.
